CANDIDATE 01

One budget module, three adapters

Strong

FILES

  • tools/check-budget.js — owns the limits
  • tools/test-budget.js — re-states 8_000_000
  • tools/test-web.py — re-states 8_000_000
  • PERF.md · README.md — prose copies

PROBLEM

The M0 budget is a domain rule, but it lives as four literals. The browser test asserts transferred < 8_000_000 on its own authority, so raising the limit would leave one check silently guarding the old number — a false pass with no failing test to show for it. There is no single place a reader can learn what the budget is.

SOLUTION

A tools/budgets.js module with one interface: limits and evaluate(measured). The Node gate, its tests (deriving the exact boundary from limits) and the Playwright check (reading the same values) all become adapters over it. Three consumers make this a real seam, not a hypothetical one.

BENEFITS

Locality: the rule changes in one file and every gate follows. Leverage: one testable interface instead of three arithmetic copies, so a boundary test written once protects the build, the browser check and the docs.

CANDIDATE 02

Split the browser check into scenarios

Worth exploring

FILES

tools/test-web.py — 257 lines, the largest file in the repo

PROBLEM

Startup, pixels, budget, device metrics and overrides all live in one main() that holds a browser, a CDP session, two contexts and a local server. Understanding one check means reading the other five; running one alone is impossible, and every new scenario lengthens the same function. That is shallow: the interface (one script, one exit code) is nearly as complex as the behaviour behind it.

SOLUTION

Each scenario becomes a function that takes a page and returns observations, with all assertions funnelled through one reporting seam (check()). --only device then runs a scenario on its own. The browser remains a single adapter at the edge; the scenario bodies become readable in isolation.

BENEFITS

Locality: a failing device check points at one function instead of line 180 of a monolith. Leverage: adding the fallback scenario later costs one function, not a re-read of the whole script.

CANDIDATE 03

Give the loader a tested core behind its DOM adapter

Speculative

FILES

  • web/loader.js — 144 lines, 3 commits
  • tools/test-loader.js — 113 lines of fake DOM to reach it

PROBLEM

The loader's only interface is the page it mutates: URL parameter, dataset attributes, overlay elements. So its tests must build a fake document that satisfies every DOM call the implementation happens to make. Change an attribute name and the fake breaks; the tests are measuring the DOM adapter, not the selection and watchdog logic where the bugs actually are.

SOLUTION

Extract the decisions into a startSession({ probe, load, clock, visible }) module that returns events (selected, failed, running). loader.js becomes the DOM adapter that renders those events; tests drive the core with plain fakes and the adapter is covered by the existing browser checks.

BENEFITS

Locality: watchdogs, visible-time accounting and one-shot fallback become unit-testable without a document. Leverage: the browser test already covers the adapter end to end, so the fake DOM loses nothing when it goes.

Speculative because M0's loader is feature-complete and stable; this pays off when M1 adds asset loading and more failure modes. Do not do it before the game loop needs it.

BEFORE — LOGIC REACHABLE ONLY THROUGH THE DOM

AFTER — CORE PLUS ADAPTER

TOP RECOMMENDATION

Start with the budget module (Candidate 01)

It is the smallest change with the largest blast radius: four literals collapse into one interface, the existing boundary tests keep working (and stop hard-coding), and the browser check inherits the rule instead of asserting its own. It also removes a live false-pass risk, which Candidates 02 and 03 do not.

Candidate 02 is worth doing before the next browser scenario lands, because each new scenario makes the monolith more expensive to read. Candidate 03 should wait for M1's asset loading to prove it needs a core.
